# 整改方案 —— 电商运营中台（对标「大厂一年工程水平」）

> 标尺：**大厂（阿里/腾讯/字节/美团等）一年经验工程师**（校招 P5 / 社招一年）的真实工作内容与能力边界。
> 输入：`docs/REQUIREMENTS_AND_FLOWS.md`（业务需求与流程设计）+ 当前代码现状。
> 目标：把项目从**「功能多、边界糊、炫技多」**收敛成**「范围清晰、基本功扎实、亮点能讲透」**——
> 即一套**一名大厂一年工程师能独立交付、并能在面试里逐行讲清楚**的作品。
>
> 两条硬约束：**下限**是每一项都要够到大厂一年的"达标线"；**上限**是任何一处都**不得越过"加分档"**，
> 绝不出现一年工程师不会 own 的东西（K8s 编排、微服务拆分、自研框架/中间件……）。越界比不足更危险。

---

## 一、整改总原则

一句话：**做减法 > 做加法**。当前项目的问题不是"做得不够"，而是"做得太杂、边界失控"。

| 原则 | 含义 | 反面（当前问题） |
|---|---|---|
| **① 收缩范围** | 只保留能讲清楚的业务闭环，砍掉与业务无关的遗留模块 | 183 个依赖、3202 行遗留路由、9 个通用工具 |
| **② 补齐基本功** | 测试、CI、代码规范、错误处理、日志——这些比"多写 3 个 Agent"更能证明工程素养 | 无 CI、宽泛 `except`、死锁靠字符串匹配 |
| **③ 可解释性优先** | 每一处代码都要能回答"为什么这么做"；答不上来的就删或重写 | 部分代码超出一年水平、无法自证 |

> 记住面试判断标准：**面试官不看你做了多少，看你对自己做的东西理解多深**。

## 二、标尺：大厂一年工程师的真实工作内容与能力边界

> 大厂对**一年经验（校招 P5 / 社招一年）**的定位很明确：**「在指导下，独立把一个模块做对、做好、能上线、能排障」**——
> 不是「设计系统」，更不是「定技术路线」。所以要用两把尺子：一把量"该做什么"，一把量"别越界"。

### 2.1 第一把尺子 · 工作内容：一年工程师的完整交付流水线

一个迭代里，一年工程师的产出是**一串可交付物**，而不是"写了多少代码"。下表是真实工作内容与达标线：

| 环节 | 真实产出物 | 本项目的对应物 | 达标线 |
|---|---|---|---|
| 需求评审 | 复述需求、确认边界与验收口径 | `docs/REQUIREMENTS_AND_FLOWS.md`（BR 清单 + 追溯矩阵） | 能说清"做什么 / 不做什么" |
| 技术方案 | 2~4 页方案文档：改哪些文件、怎么测、风险是什么 | `docs/RECTIFICATION_PLAN.md` + `ARCHITECTURE.md` | 有方案、可被评审 |
| 编码 | 小粒度提交、commit 语义清晰、遵循团队规范 | `backend/` 分层代码 + ruff 规范 | lint 全绿、CR 能过 |
| 单测 | 覆盖正常 / 边界 / 异常，mock 外部依赖 | `backend/tests/`（32 用例 / 5 文件） | 核心路径有测试 |
| 自测提测 | 能复现、能定位、给测试写清复现步骤 | `seed_demo.py` + 示例任务 + 离线端到端用例 | 别人能一键跑通 |
| 上线 | 用团队 CI/CD，**不自己造轮子** | GitHub Actions CI（lint + test） | 提交即自动校验 |
| 监控排障 | 看日志 / 探针定位问题，参与值班 | `/health` `/ready` + structlog 结构化日志 | 能按 `task_id` 串起全文日志 |

### 2.2 第二把尺子 · 能力边界：达标 / 加分 / 超纲

| 维度 | 达标（一年必须有，做不出=不合格） | 加分（做出来是亮点，仍在一年能力内） | 超纲（超过一年范畴，**不做**） |
|---|---|---|---|
| 语言与框架 | Python 异步、类型注解、Pydantic；FastAPI 路由 / 依赖注入 / 统一错误返回 | 分层清晰、依赖解耦 | 元编程、自研框架、C 扩展 |
| 数据层 | CRUD、索引、事务、连接池、schema 设计 | 幂等建表、审计表、状态可恢复 | 分库分表、读写分离中间件、自研 ORM |
| 异步与并发 | `async/await` 正确使用、超时控制 | 并发上限控制、依赖死锁检测 | 自研协程调度、高性能网络框架 |
| 工程规范 | Git 提交规范、`.env` 配置、结构化日志、异常处理 | 统一错误码、lint/format 门禁 | 自研配置中心、自研日志采集 |
| 测试 | pytest 单测、mock 外部依赖 | 边界用例、端到端集成、覆盖率门禁 | 全链路压测平台、混沌工程 |
| 运维部署 | Docker、docker-compose、健康 / 就绪探针 | CI 自动跑测试、一键启动脚本 | K8s operator、服务网格、灰度/金丝雀平台 |
| 领域建模 | 读懂业务、把业务规则落成代码 | HITL 审批、降级策略、状态机 | 完整 DDD 战略设计、领域专家级抽象 |
| AI 编排 | 会用 LangGraph 编排多 Agent、条件路由 | DAG 依赖调度、checkpointer、审批护栏 | 自研 Agent 框架、分布式编排、模型训练 |
| 协作表达 | 写文档、讲清模块、写 / 改 CR | 架构图、流程图、设计权衡 | 带团队、定跨团队技术路线 |

### 2.3 结论与两条红线

本项目的**领域建模 + AI 编排**已达到"达标线之上、加分档边缘"；**工程规范 / 依赖 / 测试 / CI** 此前低于达标线，是整改主战场。

- **下限（必须补）**：把每一项都拉到"达标"以上，不留短板被一眼看穿。
- **上限（必须守）**：任何一处**不得越过"加分档"去碰"超纲档"**。一旦出现一年工程师不会 own 的东西，面试官只需追问两轮就会露馅——**越界比不足更致命**。

> 一句话：**把"一年该会的"补满，把"一年不该碰的"削掉**，让整份作品恰好卡在"大厂一年"这条带上。

## 六、面试讲解映射（对齐"大厂一年"的叙事口径）

> 整改不只是"改代码"，更要"改讲法"。**叙事口径必须与"一年经验"一致**：
> 讲清楚"我在指导下独立交付了一个模块"，而不是"我设计了一套平台"——后者既不真，也会被追问穿。

| 面试官可能问 | 你怎么答（基于整改后） |
|---|---|
| "介绍一下这个项目" | 一句话目标 → 主管 Agent 拆 DAG → 依赖调度 → 高风险审批 → 汇总；用"物流异常处理"串一遍 |
| "为什么用多 Agent 而不是一个流程？" | 场景间有**依赖 DAG**（查异常→决策→执行→通知），单流水线无法表达；且**风险等级不同**需要分级管控 |
| "怎么做的高风险管控？" | 审批矩阵（阈值分级 auto/supervisor/manager）+ `gate()` 护栏 + 落库审计 + 恢复接口 |
| "遇到什么难点？" | ① LangGraph 0.2.4 无 `interrupt` → 降级为"落库 pending + 白名单重放"；② 依赖调度死锁检测；③ 工具失败降级 |
| "代码量不大啊？" | **主动说做了减法**：删了 183→20 个依赖、3202→~250 行业务路由，聚焦业务闭环——这本身是工程判断力 |
| "测试怎么做的？" | 审批边界、DAG 依赖、工具 IO、恢复重放 + CI 自动跑 |
| **"你在项目里的角色边界？"** | 明确自己是**模块 owner 而非架构师**：基础设施（DB / Redis / LangGraph / CI）沿用既有方案，我负责的是**业务落地**（Agent 拓扑、编排、护栏、领域工具、schema、测试、文档） |
| "这个是你写的吗？" | **如实说明**：基于开源 MIT 项目改造，我负责的部分是（Agent 拓扑、编排、护栏、工具、schema、测试、文档）——README「本人贡献」章节有清单 |
| **"有没有考虑上 K8s / 微服务？"** | **主动划界**：MVP 阶段单服务 + docker-compose 足够；上 K8s/拆分属平台与架构职责，不在我一年内的 owner 范围——**守住边界比堆技术更专业** |

## 七、明确不做的事（守住"上限"：防止越界与过度设计）

> 一年水平的项目，**做多不如做对**。以下东西**不做**，反而更专业——它们要么属"超纲档"，要么属于别的团队（SRE / 平台 / 架构）的职责：

| 不做 | 归属判断 | 原因 |
|---|---|---|
| 自研调度 / 向量库 / Agent 框架 | 超纲 | 讲不清原理，一追问就翻车 |
| 引入 Kafka / K8s / 微服务拆分 | 超纲 | 与"运营中台 MVP"不匹配，属平台/架构职责 |
| 自建监控 / 告警 / 日志采集平台 | 超纲 | 大厂用统一基建；自建既越界又讲不出体系 |
| 混沌工程 / 全链路压测 / 灰度发布平台 | 超纲 | 属 SRE / 平台团队职责，非业务一年工程师范畴 |
| 完整 DDD 战略设计（限界上下文 + 领域事件总线全套） | 超纲 | 一年只需"读懂业务、把规则落成代码" |
| 前端全栈（如果不会 Next.js） | 非本项目必需 | 后端 + 文档 + 可演示 API 已足够；硬加前端反而暴露短板 |
| 追求 100% 测试覆盖率 | 过犹不及 | 一年水平追求**核心路径 + 边界**覆盖即可 |
| 保留无法解释的遗留模块 | 负资产 | 只要讲不清"为什么在这"，就是负债 |
| 伪造提交时间 / 经历 | 红线 | 诚信风险，且技术上藏不住（活动流 / 仓库创建时间改不了） |
